## 1. 当前目标、边界与排序依据

Hua近期应证明：用户能够用它编写结构清晰的多模块本地程序，能够正确处理类型、错误、资源与输入输出，最终能够用Hua编写并构建自己的编译器。算法与Agent仍是应用方向；HTTP、数据库、GPU和自适应执行不作为首次自举的前置条件。

三步是验收顺序，开发允许需求反馈：编写Parser发现现有容器不能表达节点关系，就补相应基础；遇到二进制编码缺口，就补标准原语。每次只解决真实阻塞，避免等待“全部语法”或“全部标准库”完成才接触自举。

### 1.1 三个范围分别定义

| 范围 | 含义 | 约束 |
|---|---|---|
| 语言发行基线 | 现有公开CLI和语言已经承诺支持的规则与功能 | 本次排序不删除已实现的Task、GC、File、泛型或接口，不降低安全检查；准确记录支持、限制和拒绝条件 |
| 自举语言子集 | 第一版Hua编译器自身源码允许使用的语言能力 | 从现有稳定能力中选择；明确列出语法、类型、标准接口和模块规则，暂不使用的特性不因此失效 |
| 自举编译器覆盖 | Hua版本编译器能够接受和生成代码的源码范围 | 先覆盖自身子集；以后扩到发行基线。能编译自身不自动意味着支持宿主编译器的全部语言特性 |

A01已核定首个源码子集SB1与HC0–HC2覆盖目标；具体API签名、产物与新增退出约定仍在所属任务中核定。本文件给出推荐与验收要求，不把未确认细节填成已冻结语义。

### 1.2 优先级、影响与执行选择

| 优先级 | 判定 | 例子 |
|---|---|---|
| P0 | 当前主线的直接阻塞，或现有功能的类型/内存/资源/兼容正确性问题 | 自举子集与能力盘点、AST表示、只读能力漏洞、产物错误接受 |
| P1 | 三步主线的功能建设与验收 | 自举必需库、Parser、类型检查、HUAB编码、代际比较 |
| P2 | 自举闭环后的常规应用、工具、部署与生态扩展 | HTTP、进程、SQLite、Agent、完整LSP、可选发行配置 |
| P3 | 有真实负载与测量证据后建设的高级后端与优化 | 类型执行提速、原生缓存、GPU调度、分代/并发GC |

影响表示改动范围和兼容风险，独立于优先级：极高通常跨类型/执行器/产物，高通常跨模块或公共合同，中通常是局部库或工具。重大安全缺陷始终提升到P0；已有功能的正确性修复不受“优化后置”限制。

## 3. 保持的设计思想

- 小而稳定的语言核心；struct/interface/composition继续作为对象组织方式，不新增class继承体系。
- 静态类型、显式转换、可预测的复制/别名/修改能力；已有严格数值和注释/运算规则保持。
- 预期失败用Result，缺失用Optional，语言/预算/取消等诊断保持其边界；错误传播不隐式日志、不自动重试或回滚。
- GC管理托管对象；外部资源仍有独立关闭责任、在途保活和逻辑owner。不能为了自举简化而绕过安全规则。
- C++宿主原语承担OS/执行/必要性能边界，纯算法、组合与编译器组件优先尝试Hua源码。
- 先建立可用程序和可复现构建，再测量速度、分配和体积。高级优化不得改变语义或执行后重跑副作用。
- 长期仍保留“简洁代码、自适应执行、明确控制”，近期以明确、稳定、可测试的执行行为为基础。

| 阶段 | 核心交付 | 进入/退出条件 |

### 5.1 G1退出条件

- 发行基线和自举子集分别可查；没有“能解析所以算支持”的条目。
- 至少一个Hua AST表示试验、一个多模块符号表程序、一个失败清理程序可以运行。
- 数值/类型/能力/作用域/结果/模块的关键正反例在解释器、源码VM、移走源码HUAB中一致；不把E1标量probe当全语言验证。
- 现有公开功能的正确性问题已解决或明确限制；尚未冻结的高级语法继续拒绝，不擅自改变旧程序含义。
- 明确自举初始平台、源码规模和预算；首次推荐沿用已验证Windows x64，不把POSIX尚未验收误写成支持。

### A05-1：Hua AST表示与节点池试验（2026-10-10）

用户选择A05后，以SB1中的普通struct/enum/List/Map/Bytes实现[ast_pool.hua](../selfhost/ast_pool.hua)、[直接递归值对照](../selfhost/ast_direct.hua)和[手工构造示例](../selfhost/ast_demo.hua)。结论：**首个Parser建议沿用带池身份的NodeId节点池**。这是一项已执行的内部表示验证；没有新增语言语法、引用类型或公开标准接口，也没有冻结公共AST ABI。Parser、类型检查器和Hua字节码/HUAB编码器仍未实现。

#### 两种方案的实际比较

| 核对项 | 直接递归值：DirectNode的children为[]DirectNode | 节点池：List<Node>＋[]NodeId |
|---|---|---|
| 可表达性 | 有限递归struct可解析、检查并执行；浅树遍历/重建/clone通过 | 6个普通struct＋18种enum载荷；无需ref/ptr、用户泛型或方法 |
| 身份 | 值节点没有独立稳定身份；不能把值相等当作同一节点 | NodeId={pool,index}；仅追加、无删除/复用，增长与replace后ID不变 |
| 复制/访问 | 普通Slice可共享；不能把每次赋值都描述成深复制。clone会展开递归值 | get复制记录、子项Slice只读；add/replace显式clone子项，修改以replace写回 |
| 共享子树 | 树形访问按出现次数展开；共享例子访问7次 | 同例preorder访问7次，reachable只处理4个唯一节点 |
| 深链 | 81节点可构造；clone被当前深度防护拒绝，错误为E4007/File | 1/64/256节点深链，迭代遍历、路径复制与验证三路径通过 |
| 宽节点 | 不是本轮规模结论 | 256个子项的Block访问257个节点，顺序保持 |
| 代价 | 无稳定索引；递归调用和嵌套深复制有现有限制 | 节点/边/来源均留到Pool回收；追加重写积累旧版本，尚无压缩/删除 |

81节点案例没有File。src/value.cpp的contains_file在深度超过128时保守返回true，导致误用File不可clone诊断；这是A05当时记录的实际缺口；现已由[A09](#a09-lifetime-contract)修正为有调用来源的E4099，128层预算与资源安全规则保持。它不是所有递归值均不可用的结论；NodeId池避开了该嵌套表示。现有Parser/调用/执行步数限额保持；256是本轮实际验证规模，不是新语言上限或可无限增长的承诺。

#### 成本核对与验收

来源首次规范化/行表构建与字节数成正比，暂有to_ints临时数组；用不可变Bytes保存正文，span二分行起始表，避免每次复制整份源码string。节点读取复制固定记录和文字载荷，子项Slice共享只读；add/replace复制该节点的子项，成本与子项数有关。snapshot遍历工作列表，不能在每次get前对整个节点池snapshot。preorder按实际出现次数计费，DAG可能大幅展开；reachable用Map去重并排序ID，计入Map查找和排序成本。重写保存映射与新增节点，不宣称零复制、零分配或O(1)重写。未测真实峰值内存/GC停顿，逐路径墙钟时间只作运行记录，不能推导性能优势。

[专项测试](../tests/selfhost_ast_pool_tests.py)共26例／296检查；两种Release构建均通过SB1、AST、源码VM和删除全部本地.hua依赖后的HUAB。7节点表达式类型/文本/顺序/span与[C++参考](../tests/a05_ast_oracle.cpp)一致；6份空/EOF/BOM/CRLF/CR/Unicode/组合字符来源的36个字节位置及完整规范化字节一致。正反例覆盖18种载荷、稳定ID、多来源、跨池/越界、伪造span、边/元数拒绝与原值不变、只读/clone/写回、共享子树、重写与预算、深链/宽节点及递归值边界。

HUAB为**宿主C++编译器**生成：模块使用Result<void>，正确写入现有v7、ABI1；删除源码后复核check/run。这不是Hua输出HUAB，也不冻结C01只能用v7。两构建相关回归各5/5，范围是binary_collections、language_structure、selfhost_lexer、language_baseline、selfhost_ast_pool；之后仅针对最终Bytes/多来源变动重跑A05通过。证据build/a05/及build-python-off/a05/中的ast-pool-results.json、focused-final.log、ast-final.log；POSIX没有新增实测。

### 7.1 代际验收具体规则

C0是现有C++编译器。C0编译同一份Hua编译器源码得到compiler1.huab；现有VM运行compiler1，让它编译同一源码得到compiler2.huab；VM运行compiler2得到compiler3.huab。代际使用同一冻结源码、标准模块、配置与输入。

第二代/第三代至少比较：接受/拒绝的程序集合、错误分类与位置、运行输出/结果/副作用、模块与函数身份、指令/常量/类型及格式版本。若时间戳/路径等非语义字段存在，C01须先明确剥离/规范化方案；同一确定性条件下应进行字节比较。不能比较失败后临时挑选的字段来掩盖差异。

独立对照保留C++前端和解释器；Hua版本不得把sema/bytecode/encode工作委托给C++私有入口后宣称已实现相应组件。共同依赖C++ VM、GC与OS标准原语符合本阶段边界。

### 7.2 G3退出条件

- 编译器主体由Hua实现；其自身所有源码构造均被自己接受并编译，B中的依赖可明确获得。

### 与成熟实现的设计对照

这是机制对照，不是同功能同环境的跑分；Go/C++原生编译与Hua解释执行不能直接换算速度倍数。

| 参照 | 官方实现的具体机制 | Hua可借鉴的方向 |
|---|---|---|
| Lua | VM通过指令操作栈上寄存器槽，并提供表访问快路径。[官方VM源码](https://www.lua.org/source/5.4/lvm.c.html) | 预绑定局部/字段访问、缩小热路径；仅凭Lua使用寄存器不能证明Hua必须改寄存器VM |
| CPython | LOAD_FAST按槽位取局部；vectorcall通过参数数组传递，减少调用转换。[字节码源码](https://raw.githubusercontent.com/python/cpython/3.12/Python/bytecodes.c)、[调用协议](https://docs.python.org/3.12/c-api/call.html) | 先改善局部槽位和参数传递；Python说明栈机也能优化，Hua值复制语义仍需独立保留 |
| Go | 编译阶段有专门类型IR/SSA、逃逸分析与栈帧布局，并提供阶段计时。[编译器说明](https://go.dev/src/cmd/compile/README) | 编译信息提前固化、分阶段观测、避免每次执行重新发现静态事实；不把立即增加原生后端当唯一解决办法 |
| C++/Clang | ASTContext集中管理AST，使用专用分配器；源码位置轻量，声明查询有专门索引。[ASTContext](https://clang.llvm.org/doxygen/classASTContext.html)、[内部设计](https://clang.llvm.org/docs/InternalsManual.html) | 编译数据专用布局/寿命与轻量ID，通用运行时Value不是编译器数据的唯一物理表示；对象池/Arena需先明确根与生命周期 |
