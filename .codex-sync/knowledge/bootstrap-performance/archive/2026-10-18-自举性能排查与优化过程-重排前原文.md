## 1. 目标、设计原则与责任边界

### 1.1 本轮用户要求

- 先理解成熟实现的性能与设计，再解释 Hua 的差距；不再反复让完整负载跑到超时。
- 对真实热点完成因果分析，必要时从编译数据表示、Value、VM、分配和 GC 底层修复。
- 保持语言最初方向及已确认合同，优化不能降低安全性或通过更换测试含义取得验收。
- 每次优化留下可接手、可复核的记录，保留失败证据，避免相同设计错误重新出现。
- 可以使用源码审计、官方资料、成熟实现对照、系统采样、诊断构建、差分测试、生成输入及故障注入等手段；手段必须服务于具体假设。

此前“不限时测试”是已有授权，不需要重新请求同一权限；生产单次 600 秒等预算仍保持。授权不构成无目的重复运行的理由。本文用实验目的、输入规模、停止条件和晋级闸门控制资源消耗。

### 1.2 保持的语言原则

依据 [当前设计思想](设计决策与未决事项.md#next-generation-direction)、[语言规则](语言设计与类型规则.md)、[E0/E1 运行时合同](运行时与扩展设计.md)：

| 原则 | 本次优化的约束 |
|---|---|
| 小而稳定的核心，静态类型，显式转换 | 优先改变内部物理表示与执行成本；不为自举增加特殊业务语义、隐式转换或第二套类型规则 |
| 可预测的复制、别名、只读与 mut 能力 | 保持固定数组/struct 值隔离和 Slice/List/Map 的既有共享规则；只读共享不能升级可写 |
| Optional 表达缺失，Result 表达预期失败 | 不以跳过 Result 包装/错误分支的检查换速度；内部可减少已证明冗余的物化 |
| 求值、返回、defer、失败有明确顺序 | 保持参数完整求值与检查时点、返回值保存时点、清理顺序及首错优先级 |
| GC 管托管数据，资源有独立责任 | File/Task/在途资源保活、取消与退休不因池化、COW 或 Arena reset 失效 |
| 简洁代码、自适应执行、明确控制 | 静态已知的信息尽量提前固化，运行期保留真正需要的动态检查；优化决定有证据和解释 |
| 宿主提供 OS 与必要性能原语，编译算法优先 Hua | 可优化通用布局、调用和存储；不能把 Hua 分析器偷偷替换成宿主完整编译，再称为自举成功 |

长期 HXE、Smart Memory、effect、Explain 方向可以指导设计：稳定身份、明确寿命、类型布局和可解释决策优先。当前 Typed HIR/MIR 仅有标量子集；不能声称已覆盖自身编译，也不把完整 AOT/JIT、寄存器 VM、GPU 或全运行时改写为首次自举的强制前置。

**可优化实现，不可把语义成本误认为必须逐处实际复制。** 反之，只读也不自动证明可以消除值快照：全局别名、mut 实参、defer 和延后写入都可能改变观察结果，必须证明安全。

## 2. 当前验收在做什么

实际入口：[测试脚本](../tests/selfhost_archive_budget_tests.py)、[内部编译器入口](../selfhost/archive_main.hua)、[公开入口](../selfhost/compiler_main.hua)、[机器合同](../selfhost/contract.json)。

| 阶段 | 操作 | 计时与意义 |
|---|---|---|
| C0 准备 | 收集 archive_main 的非 std 导入闭包；复制独立的执行源码与待编译源码；由原生 C++ hua build 生成 bootstrap-component.huab | 准备时间单列，不计入后面的自身编译 600 秒；正式执行源码与输入源码哈希一致 |
| C07 自身编译 | C++ VM 执行 Hua 编译器组件，读取另一份同源码闭包；分析、降级、生成、验证、编码并发布 self.huab | 600 秒监督针对这一次调用；源程序不由 C++ 前端代编译 |
| 产物检查 | 既有独立 C++ reader/check 检查 self.huab | 验证格式和字节码，不能单独证明前端语义全部正确 |
| 源码移走 | 移除测试目录 current-source 下的输入 .hua 副本 | 不删除仓库源码；“无源码”指不重读这些外部源文件，HUAB 仍可携带诊断源码信息 |
| 编译器行为 | 原 Hua 编译器与生成的 self.huab 编译同一多模块小例；比较 receipt、HUAB 字节并运行，输出均为 2 2 | 证明生成组件继续工作；同实现一致性不替代独立语义 oracle |
| C08 后续 | 冻结同源后的 compiler1 → compiler2 → compiler3 | 当前未进入，不能用前述小例或 C++ 引导组件代替多代证明 |

当前走内部 C07 JSON receipt 入口，公开 CLI 和 A06 失败协议另有回归。当前 HUAB 仍由 C++ reader/VM/runtime 执行，不是原生机器码可执行文件，也不是运行时已经用 Hua 重写。

生产约束仍为：500,000,000 VM 步骤、调用深度 128、GC 间隔 65,536、单次监督 600 秒、报告上限 16,777,216 字节。VM 步骤不是机器指令数，也不能反映一条指令触发的全部复制、字符串、容器和 GC 成本。16 MiB 是报告上限，不是 self.huab 文件大小上限。

600 秒只作为失控保护；性能目标必须另行根据本机基线、输入规模和复杂度制定。

## 4. 成熟实现的比较方法

### 4.1 三层比较，避免错误排名

| 层级 | 对照方式 | 可回答 / 不可回答 |
|---|---|---|
| 工程量级 | 官方公开的成熟编译器真实构建记录 | 说明合理工程表现；不同机器/语义/并行度不能直接换算 Hua 倍数 |
| 同机相同输入 | 原生 Hua C++ 编译器与 Hua 编译器处理相同闭包，阶段和输出范围分别记录 | 定位差距在哪层；算法不同，不能归因于语言执行速度一项 |
| 同机相同算法 | 从实际热点提取最小内核，在 Hua 和一种原生实现、必要时一种解释/JIT 实现执行相同转换 | 区分算法工作量与每次操作成本；内核快不能代表完整编译器已经快 |

先复用本机可用的 C++ 与 Python；Go/Rust/Lua/Node 等只在提供额外辨别力时引入。只补齐选定实验必需环境，记录版本、构建选项和依赖；不为语言排名安装一套无关工具链。

内核必须由实际热点导出，固定输入和输出 oracle：节点读取、结构边界复制、来源实例化、字段投影/合并/相等、摘要依赖传播。端口遵守同样的复制与共享约束；若使用不同物理表示，标注为“实现方案比较”，不声称仅比较语言。

不能让一个实现输出摘要、另一个输出完整 JSON；不能混用进程冷启动、组件加载、稳态执行、不同线程数、诊断构建与 Release。需要完整产物时测完整产物，摘要实验只用于隔离成本。

## 5. 每次优化必须遵守的流程

### 5.1 闸门 BO-G0–BO-G5

BO-G* 专用于单次优化晋级；项目 G1/G2/G3 保留原有语言基础、标准库和自举整体验收含义。

| 闸门 | 必须具备的材料 | 未满足时的动作 |
|---|---|---|
| BO-G0 问题定义 | 一个明确现象、固定输入、当前真实实现、已有/未知结论、待验证假设 | 先补只读审计，不直接修改多个层 |
| BO-G1 归因 | 热点的 exclusive/采样证据、相关操作数与增长曲线、能够区分假设的最小实验 | 选择更小可解释实验，不重跑完整 600 秒 |
| BO-G2 方案审查 | 至少维持现状与一个替代方案；语义、复杂度、内存、兼容和实现成本；预计能消除的工作 | 不能只写“加缓存/换 GC/换 VM”；先补设计 |
| BO-G3 局部闭环 | 改动前可观察问题，改动后相同输入语义对照通过；真实热点指标改善且墙钟/CPU 有解释 | 失败即停在该改动，不叠加下一批优化掩盖差异 |
| BO-G4 集成准备 | 受影响回归、至少两个规模的真实缩小闭包、阶段成本与预测误差、正确性边界明确 | 局部计数下降不足以晋级完整自身 |
| BO-G5 正式验收 | 未插桩相同执行链完成，独立 reader、移走源码后的编译器行为和产物核对通过 | 一次失败回到有变化的诊断假设；不循环重试 |

门槛以证据为准；没有工具的采样不可用写清替代方法。普通内部优化在已授权范围内连续推进，不反复请求用户确认同一权限；涉及公共语义、兼容格式或安全合同变化时，先形成具体差异方案，遵守既有设计确认要求。

### 5.2 实验纪律

1. 每轮只针对一个主要假设；需要相互依赖的改动，先解释为什么不能拆开，保留可区分贡献的对照。
2. 每个新输入/版本先执行一次受控样本。输入规模可选 16/32/64/128，实际按完成成本选择；固定嵌套深度和其他维度，一次只变化一个维度。
3. 首次诊断超时、内存异常增长、语义差异或输出不完整，结束对应进程树并保存阶段与命令；不把超时当成源码预期错误。
4. 只有运行足够短、结果一致且需要判断噪声时，再做最多三组成对 A/B 或交替 A/B/B/A 样本；原始值全部保留，小样本不宣称统计显著。
5. 不复跑“相同代码 + 相同输入 + 相同配置”的完整失败负载。新增采样器只允许在更小输入先校准；放大前写明新信息与停止点。
6. 若成本随字段、来源、调用边明显超线性增长，先解释增长来源；不能用更小负载隐藏问题，也不能单凭四个点断言严格复杂度阶数。
7. 工作量、copy/move 次数、托管对象头部字节、累计分配字节、存活字节、RSS/工作集分别统计。现有 tracked_object_bytes 不覆盖 string/map/vector 的全部后备存储，不能当真实总内存。
8. 采样、计数、插桩各有开销。现有 HUA_INTERNAL_PROFILE 使用原子计数；不能把其热点分布和时间直接当正式构建结果。新增计数先粗粒度，必要时用诊断专用线程局部/阶段归并，保持并发和嵌套作用域正确。
9. 诊断数据写独立受限输出，阶段边界及时保存；不得混入公开 CLI 成功/错误输出或让 trace 自身成为主要 I/O。
10. 预测使用 `T_new ≈ T_other + T_hot / speedup` 等可解释分解；没有热点份额就不给整体加速承诺。优化某项 20% 的计数不等于总时间快 20%。
11. 每次改动后只运行受影响的必要检查；通过后不重复扩展无关测试。底层 Value/VM/GC 改动按影响扩大到全部必要语义与资源路径。
12. 实验不自动修改 production 步数、深度、GC 间隔、格式或原子发布规则；测试监督变化单列，不冒充编译器加速。

| 编译器编码/发布 | 指令/来源/CRC/长度独立校验、发布原子性、失败保留旧文件、生成产物实际运行 |
| 执行范围 | Windows Bridge OFF 既有结果只算该范围；ON/POSIX/其他架构与全套仅在实际验证后记录 |

表示优化应优先保持完整报告字节一致。确需改变内部调度计数时，先列出允许变化的字段，其他字段全量比较，并保留独立 oracle；不能用两个同源实现相同输出替代正确性。

## 8. 需要阻止的重复错误

| 之前容易发生的错误 | 以后必须提供的检查 |
|---|---|
| 删大参数后按静态字段数量宣布整体提速 | 相同输入的运行时间、相关字段/分配数据及总成本解释 |
| 加缓存却没有生命周期/失效键 | 每个缓存的会话、身份、版本、可变性、清空点及陈旧反例 |
| 全量 clone 改浅共享或全部 mut | 全局/实参别名、返回/defer 快照、Task/资源反例与所有写入路径证明 |
| 为避免复制先复制再覆盖所有字段 | 列出实际需要读取/修改的项，统计复制与覆盖数量，比较按需构造 |
| 节点数变化很小便认为分析工作量稳定 | 字段/来源集合、路径展开、摘要体积、迭代与 GC 图规模 |
| 把包含时间相加或把计数构建当正式时间 | exclusive 定义、嵌套关系、采样扰动和未插桩对照 |
| 只优化套件反复启动，称单次编译更快 | 冷启动、加载、稳态编译、输出、套件总耗时分别记录 |
| 提高预算、少做检查或用宿主代编译 | 对照合同、步骤/报告模式、发射来源与独立 reader 证据 |
| 只验证变小的玩具输入 | 至少两个规模的真实缩小闭包，保留触发问题的数据形状 |
| 只比较两个同源实现 | 独立构造预期、原生 oracle 或已有冻结正确结果 |
| 同版本完整超时后继续试运气 | 失败分类、新假设、改动和新信息目标；没有这些不放行 |
| 有局部收益仍无限叠加微优化 | 计算可消除时间上界；不足以解释总差距就转主要结构问题 |
| 一次重构 Value/VM/GC/分析器多个层 | 拆成可归因补丁；确实不能拆时保留分层原型对照 |
| 在未测平台或未提交源码上泛化完成 | 精确执行范围、源码清单、dirty 状态和未测项 |

该流程不能承诺消除所有错误；必须通过可检查的闸门阻止同一错误未经复核再次进入完整验收。

### 12.2 测量方法与不能混用的边界

Hua使用程序内monotonic_ns测量循环，排除进程启动、HUAB读取和最终校验/打印；每项一次正常样本，计数来自单独的诊断执行。毫秒量级样本仍受调度、缓存及计时噪声影响；例如V=1的首/末匹配逻辑相同但时间不同，故不声称统计显著或精确提速比例。

C++每组从1024次开始，累计被测循环时间不足20ms时倍增独立批次数，达到20ms后停止；设131072批硬上限，实际未触及。每个批次独立初始化，报告批次数、总操作数、checksum和纳秒；校准所执行的工作包含在进程总用时内。循环中的编译器内存屏障让中间值可观察，避免直接把循环删掉；计时、屏障和静态优化约束仍是测量的一部分。参考[Google Benchmark关于优化屏障的说明](https://github.com/google/benchmark/blob/main/docs/user_guide.md)，并未声称使用了完整Google Benchmark框架。

C++ Value组每轮显式创建/复制两个StructData；Hua复制组每轮为两次Struct复制加一个作用域环境，共三次托管分配。原生组没有VM分派、环境和动态类型检查；std::variant还使用已知的活动值表示及不同的访问分派。这五组用于逐层分离成本，不能把它们的时间之比称作C++与Hua的通用速度差。

本机sizeof(Value)=144、各组sizeof(std::variant)=16字节；Value的144字节不包括StructData、map节点、string存储和托管堆记录，不可据此计算完整内存倍率。[C++标准草案variant说明](https://eel.is/c%2B%2Bdraft/variant.variant)规定活动值嵌套在variant对象中；这里各分支的载荷类型大小相同，实测对象大小不随分支数增加。这不是对任意variant类型作16字节承诺。

四种V下，两条Hua复制路径**均为9234 VM步骤、2048次Struct复制、3072次托管分配、0次GC**。现有enum字段复制量依次为4096、18432、67584、122880；两字段结构均为4096。V=59时字段工作量恰好减少30倍；Hua本次时间约为原来的1/7.39，C++同一复制函数的活动布局约为全布局的1/14.81。它们是该内核的观测，不是已上线改进或整体自举提速预测。

这组对照排除了“只是VM步骤数增加”“只是GC”“只是托管分配次数增加”对复制增长的解释。C++全字段/活动字段组保留同一Value和复制函数，仍呈相同增长/平坦趋势，证明非活动字段遍历、字段节点分配及值/名称处理构成结构性成本。尚不能据此把真实编译器总CPU的某个百分比归给copy_value。

对于m轮、单载荷V分支：当前布局F=V+1，复制内核恰有2mF次字段访问；活动布局F=2时为4m次。普通Struct复制使用有序map尾部hint，不能把它误记为每个字段都做完整树查找；即使已有该优化，仍需复制所有F个字段并创建节点。模型是字段工作量O(mF)，包含载荷深度、键长度等时还需加入相应成本。

### 12.4 构造、匹配与产物规模：三个问题分别解释

- 构造：V=59时Hua enum约11.550微秒/轮，两字段结构约2.029微秒；C++全字段约5.060微秒，活动字段约0.340微秒。两条Hua路径均4次托管分配/轮，但现有enum需初始化所有非活动nil字段；VM步骤从V=1的23570增至V=59的142354，对照结构始终23570。
- 复制加首分支读取：V=59时Hua enum约7.764微秒/轮，结构约1.421微秒。现有enum有2次Struct复制及6次托管分配/轮，对照结构为1次Struct复制及4次托管分配/轮；因此这项不能称作仅改变物理字段数量的严格对照。
- 复制加末分支读取：V=59时Hua enum约13.620微秒/轮，结构约6.131微秒。两者相对于首分支，均恰多1024*5*(V-1)条VM步骤。即使活动载荷压缩成功，顺序匹配仍有随分支位置增长的成本；不能承诺紧凑布局使所有match变O(1)，也不在本轮叠加分派优化。
- 原生C++控制组保持顺序标签查找：V=59末分支约5.713微秒（全字段）与0.437微秒（活动字段）；std::variant本例约1.30ns，采用另一种已知类型的访问分派，不能用其数值反推完整VM应达到相同水平。
- 原生及Hua降级均为每一个变体生成包含全部布局字段的构造函数。该单载荷模型生成V*(V+1)个字段初始化项，静态生成工作O(V²)，而单次执行构造不是O(V²)。四规模enum HUAB为20888/36071/165674/454709字节，结构对照为21338/26112/42526/60994字节。V=59时约7.46倍；产物还包含导入、函数、匹配和调试元数据，不把总文件字节全部归给构造器。

### 17.2 从源码推导并验证的复制模型

`src/value.cpp`的const复制递归复制Struct字段及Result载荷；唯一右值已有原地传递路径，但仍递归处理后代。`enforce_type`的Result分支在递归约束载荷后重新`copy_value`并分配包装，即使预期类型元数据相同。它同时承担上下文转换/只读传递等职责，不能简单删掉。VM普通参数先复制再约束，返回在defer之前保存快照，之后执行返回约束；调用方Bind再次约束并保存。这些阶段共同解释下表。

原生辅助函数每次传递的工作量（总量乘N；字段复制再乘W）：

| 操作 | Struct实例复制 | const Result包装复制 | 新托管对象 |
| --- | ---: | ---: | ---: |
| const复制／共享右值 | D | R | D+R |
| enforce_type／原生borrow辅助 | D×R | R×(R−1)/2 | D×R+R×(R+1)/2 |
| 普通参数 | D×(R+1) | R×(R+1)/2 | D×(R+1)+R×(R+3)/2 |
| 返回快照＋enforce_return | D×(R+1) | R×(R+1)/2 | 同普通参数 |
| 参数＋返回辅助 | 2×D×(R+1) | R×(R+1) | 2×D×(R+1)+R×(R+3) |
| 唯一右值 | 0 | 0 | 0 |

唯一右值的`copy_move`调用仍为N×(D×W+R+1)，因此零新托管分配不等于O(1)。List三个长度在普通copy/enforce/调用辅助内均无新载荷对象、无Struct复制；深clone不在此项中。

实际Hua的完整语句边界如下；“返回”包括调用方接收绑定，不与只调用原生enforce_return混为一谈：

| 操作 | 每次Struct复制 | 每次const Result包装复制 |
| --- | ---: | ---: |
| 局部let绑定（Bind带推断后的类型） | D×max(1,R) | R×(R−1)/2 |
| 普通参数 | D×(R+1) | R×(R+1)/2 |
| 返回＋接收绑定 | D×(2R+1) | R² |
| 参数＋返回＋接收绑定 | D×(3R+2) | R×(3R+1)/2 |
| mut Struct借用 | 0 | 0 |

### 22.5 下一候选和实施顺序

优先只改边表：每个对象开始前记下当前flat.size，按原heap_edges顺序把目标追加到连续flat数组并累加入度，最后补offset[V]。标记时遍历flat[offset[i]..offset[i+1]]，保持对象顺序、边顺序和重复引用次数；不增加一次对象字段遍历，不把对象数误当边数上界。先保持原地址索引和回收间隔，避免同时改三层。

### 26.4 完整规模的规划场景与边界
