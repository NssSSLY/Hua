# 能力分析性能路线设计方案（审阅稿，2026-10-23）

状态：用户已同意“算法优先、标准库跟进、VM另立”，并授权S0与S1。S0已测、S1已实施待接受（2026-10-23，见过程文档S0/S1行）；S2–S4未授权。HUA-D008嵌套成员写假阳性已登记为P0，按用户要求暂不修复。所有数字来自`build/bo11-beyond-20261023/`等已存证据；“估计”一律是推算，不是实测。

## 1. 问题与量级

- capabilities.hua单模块输入（闭包8个模块）：能力分析阶段931937087步（生产预算5亿的1.86倍），361.8秒，9轮。整次运行1030005824步，但因HUA-D008假阳性在types阶段后结束，降级/验证/编码未计入。
- 真正的目标是C07完整自身：14个模块一次编译，全部阶段合计≤5亿步，保守普通时间≤400秒。该输入的能力阶段尚未测过，只知道必然大于单模块。
- 结论：需要的削减量至少是2倍以上，很可能是4–6倍，不是常数级微调能解决的。
- 原生对照（2026-10-23，单次墙钟）：`hua check selfhost/capabilities.hua` 14.18秒，`hua check selfhost/archive_main.hua`（14模块）18.68秒。说明：(1) 原生C++分析在同类输入上已经很慢，问题首先是算法与抽象域规模；(2) Hua VM执行同类工作约慢27倍（≈381秒），属于常见解释器与C++的差距范围，重写VM能得到的是常数倍，不是算法级削减；(3) 完整输入约为单模块的1.3倍（原生口径），可粗估14模块的能力阶段约12亿步，以S0实测为准。
- 一致性约束：C04对照的基准是原生编译器的诊断。任何改变精度的方案（S3）都必须在原生sema与Hua分析器两侧同步，否则两边诊断会分叉。

## 2. 成本从哪里来（实测分解）

能力阶段931.9M步可以从两个正交角度拆分：

**A. 按访问轮次——晚期轮次的重复访问**

| 函数体 | 访问次数 | 合计步骤 | 最后一次访问 | 假如只访问3次（按最终规模） |
| --- | --- | --- | --- | --- |
| statement | 8 | 395.0M | 74.4M | 223.2M |
| analyze | 8 | 197.3M | 41.0M | 123.1M |
| expression_body | 7 | 157.9M | 31.9M | 95.6M |
| invoke | 6 | 49.2M | 9.7M | 29.0M |
| expression | 8 | 9.3M | 2.0M | 6.0M |
| 合计（递归簇） | | 808.6M | | 476.9M |

- 第5–8轮只重访递归簇，每轮新增的来源很少：statement在6→7只多150条，7→8不再变化；expression_body 6→7只多90条；expression只多15条。但每次重访都要完整重算一个7400万步的函数体。
- 原因之一：`analyze`以`for name, f in functions`遍历，`functions`是`map[string]Function`，迭代顺序是键的字母序，不是“被调用方优先”。helper（conservative_value、merge_view、merge、instantiate…）的新摘要要再等一轮才传到上层，于是形成逐跳传播的长尾。
- 注意：早期轮次出现过来源被移除（statement 2→3 −46，3→4 −14），说明分析不是严格单调的。换遍历顺序后，最终事实可能与现在不同，必须有校验关卡。

**B. 按helper——每次访问内部的集合循环**

| helper | 独占步骤 | 占比 | 性质 |
| --- | --- | --- | --- |
| instantiate_view | 247.8M | 26.6% | 每来源字符串拆分、查表、并入（含fact.origins并集内循环） |
| merge_view | 115.2M | 12.4% | 纯集合并集 |
| same_flags | 69.5M | 7.5% | 纯集合相等 |
| note_prefix | 59.7M | 6.4% | 路径前缀索引插入 |
| storage_aliases / put | 37.3M / 36.5M | 4.0% / 3.9% | 字段表扫描 |
| same_storage | 30.5M | 3.3% | 纯集合求交非空 |
| field_fact / same_view / projected / split_origin / key | 25.4M / 22.3M / 17.7M / 15.0M / 19.9M | 合计约10.7% | 每视图/每来源小操作 |

VM每条指令计1步；内建调用无论处理多少元素，都只有常数条指令。BO-07已有先例：保留`json.encode`作为`same_fields`的精确快路径，步骤比逐字段循环少13倍。

**C. 每次访问的规模本身**

来自宽记录（Environment 272、State 188、Value 87字段，8层投影）的字段视图，各带一份来源集合；新分配来源在每个调用点各有一份副本。候选A已证明：只压缩不同标签数，不会减少每次处理的“视图×来源”条目。

## 3. 目标与验收关卡

1. 第一里程碑：capabilities.hua单模块能力阶段≤3亿步（给其他阶段留余量），事实与诊断不变。
2. 第二里程碑：14模块完整输入的能力阶段与全部阶段在5亿步内，保守时间≤400秒；之后才按原流程执行C07。
3. 每一步的正确性关卡（沿用已有工具）：C04完整套件；新旧分析器185输入报告逐字节对照；实例化与元数据隔离；type_rules/ast_pool/Parser/Modules/留出5个真实输入编译HUAB逐字节相同；capabilities.hua输入的能力事实（Model.facts）新旧对照。改变精度的步骤另加：差异逐条列出并由用户确认。
4. 生产预算（5亿/128/GC65536/600秒/16MiB）不变；超5亿只用诊断工具的显式标志。

## 4. 方案（按建议执行顺序）

### S0 先测清完整目标（只测量，不改代码）

- 用`--beyond-production-diagnostic`对14模块完整输入（selfhost/archive_main.hua）测能力阶段步骤与轮数。HUA-D008会让编译在types之后停止，但能力阶段会完整跑完，所以该阶段的数字有效；降级/编码阶段要等假阳性修复后才能测。
- 输出：完整输入的能力阶段步骤、各函数体访问曲线、helper分解。它决定后面S1–S3要做到哪一步。
- 预计耗时：按每秒约260万步，若为10–30亿步则需7–20分钟；监督上限2小时。

### S1 收敛调度：被调用方优先＋簇内工作表（语义中性目标，首选）

- 改动：在探测第1轮结束后（`s.dependents`已建好），对调用图求强连通分量，按逆拓扑序（被调用方优先）排定后续各轮的访问顺序；簇内仍用现有dirty标记作工作表。轮次上限32、未收敛保守回退、最终验证轮及首错规则都不变。
- 预期：helper摘要在调用方访问前已稳定，消除逐跳传播的长尾。估计递归簇访问次数从6–8降到约3次，节省约3.3亿步（808.6M→约477M），能力阶段约9.3亿→约6亿。数字是估计：簇内互相递归的边仍需迭代。
- 风险：分析不严格单调，换顺序后最终事实可能变化；`passes`计数会变（属内部统计）。按第3节关卡验证；若事实有差异，逐条判断是否只是更精确或更保守，再交用户决定。
- 工作量：小。只改`analyze`的调度循环，加一个Tarjan SCC（约40行Hua）。

### S2 原生集合原语（常数级加速，需走标准库流程）

- 改动：在标准库路线S1c容器候选中，为`map[string]bool`形式的集合提供原生操作，并用于`merge_view`、`same_flags`、`same_storage`及`instantiate_view`中的`fact.origins`并集内循环。候选形态：`union_into(dst mut map[string]bool, src map[string]bool)`（只读标志取或）、`equal(a,b) bool`、`intersects(a,b) bool`。名称、所属模块（`std.collections`或扩充现有接口）、复杂度与两执行器一致性按标准库冻结流程定。
- 预期：上述循环直接占约2.15亿步，加上instantiate_view内循环的一部分，S1之后估计再降25–35%（约6亿→约4–4.5亿）。墙钟时间同样下降，但宿主侧工作仍计入600秒。
- 风险与边界：这是新的公开标准库接口，需要文档、AST解释器/VM/HUAB一致性测试与预算行为说明，不是只为编译器开的内部后门；“内建按常数计步”是现有规则，不新增特殊计数。
- 工作量：中。C++实现约百行，加测试与文档。

### S3 抽象域界限：路径深度k限制＋集合上限＋前缀感知别名（S0显示仍不够时）

- 改动：`projected()`把来源路径截到k层（现在只在512字符处截断）；单个视图来源数超过N时，按所有者折叠为根来源并保留只读标志；`same_storage`改为前缀感知（`owner|a`与`owner|a#@b`视为可能别名），保证折叠后仍然保守。
- 预期：直接限制每次访问的“视图×来源”条目，这是C节规模的根源；削减幅度取决于k与N，需要先用诊断副本做k=4/2、N=32/64的实验矩阵再定。
- 风险：会降低精度，可能产生新的保守E3003。合同只规定“最多8层、未知保守回退、精确别名证明不是语言保证、动态E4007保持”，降低精度在合同允许范围内，但用户可见诊断可能变化，必须逐条审阅差异。
- 工作量：中到大，涉及抽象域定义和多处一致性。

### S4 若仍不够：预算或执行路线（需用户决策）

- 提高`compiler`档位步骤上限，或评审HUA-D028（类型化执行/原生后端）。后者主要缩短墙钟时间，对按指令计数的步骤上限基本无效，除非同时改变计量方式。只在S1–S3都有实测数据后再讨论。

### 已排除

- 候选A（去掉调用点来源字段路径）：已实测，不同标签降5.4倍，但处理条目和步骤都没有下降，已回退。
- 来源集合共享/驻留：最终摘要213个写对应213个不同集合，几乎没有重复。
- 借用C++分析结果：违反“不挪用C++编译链冒充Hua自身成功”的既定原则。

## 5. 建议执行顺序与决策点

1. 批准S0（只测量）与S1（调度，语义中性目标）。S1完成后，按关卡报告事实差异与步骤。
2. 依据S0与S1结果，决定是否进入S2（新标准库接口，需你确认接口与模块归属）。
3. 若S1+S2仍达不到第二里程碑，再审S3的实验矩阵；S4最后讨论。
4. HUA-D008假阳性保持登记。注意：修复它可能改变能力阶段步骤，S1–S3的前后对照应在同一份源码上进行，修复时重新取基线。
